# Security review

Scope: one native StatusForge process, a local web client, loopback fixtures, and DynamoDB Local 3.3.1 on `127.0.0.1:8000`. This is a **local-only** development release, not a security certification or a hosted-service threat model. Evidence below names the automated test or the manual check that established each control; a listed test establishes only the behavior it actually exercises.

## Dependency gate operation

From the repository root run `make security-check`. Node 24/npm 11, Go 1.27 and Python 3 are required; install web dependencies with `npm --prefix web ci` first. The tool module `tools/go.mod` pins `govulncheck` and `gitleaks` outside the backend product module; `tools/go.sum` locks their graph. The npm audit threshold is **low and above**, production only, so any reported advisory fails. The licence gate follows the compiled `cmd/statusforge` Go dependency graph (not test or tool imports) and the installed npm production graph (`npm ls --omit=dev --all --json`). It reads Go module licence text and installed npm `package.json` licence IDs; every ID must be MIT, BSD-2-Clause, BSD-3-Clause, Apache-2.0, ISC, or a dependency-specific licence with an explanation in `infrastructure/scripts/security/licence-exceptions.json`. Missing or unrecognized licences fail, and so does any package installed locally but absent from `package-lock.json` (run `npm --prefix web ci`). Composite SPDX expressions pass only when every component is allowed. New exceptions require a recorded rationale, not a blanket skip. Scan logs redact findings; inspect the location and rotate/revoke real secrets before treating a hit as a false positive. Do **not** add this gate to `make verify`.

The gate also covers `infra/` (install with `npm --prefix infra ci`): `npm audit --omit=dev` through
`infrastructure/scripts/security/npm-audit.py`, and the licence walk over its production tree, including
`aws-cdk-lib`'s bundled dependencies (`case` is `MIT OR GPL-3.0-or-later`, used as MIT; `minimatch` is
`BlueOak-1.0.0`, a permissive licence; both have reasoned entries in `licence-exceptions.json`). Only `infra/`
can carry audit exceptions; the `web/` audit still fails on any finding.

The Go licence walk also follows `cmd/lambda-planner` and `cmd/lambda-worker` as `make lambda-build`
builds them (linux/arm64, `-tags lambda.norpc`). `github.com/aws/aws-lambda-go` (Apache-2.0 AND MIT-0) has a
reasoned entry in `licence-exceptions.json`.

## Known gaps and unverified claims

- No login, authorization, account isolation, CSRF token or multi-user access control. The management API is unauthenticated even though bound to loopback; local processes and browser requests are an attack surface. The Host/Origin/Content-Type guards reduce drive-by requests but do not authenticate callers. Do not expose or proxy it to LAN/public networks.
- No TLS for the HTTP UI/API, target fixture, notification receiver or DynamoDB Local. Local transport is not suitable for remote clients. There is no hosted DynamoDB or AWS deployment; hosted TTL latency, IAM policies, quotas, failover, cloud networking and service security are unverified.
- No external monitor targets are approved or tested. Loopback-only allowlists do not constitute general-purpose SSRF protection for a future remote-target design. Fixtures and sample-job controls are deliberately unauthenticated on loopback.
- Secret scanning has known-safe fixture allowances and cannot prove the absence of every secret. Local `.env` and exports are private but vulnerable to the machine's owner or compromised local processes. Git history scanning covers only history fetched into this clone (CI uses `fetch-depth: 0`); it cannot erase a previously disclosed secret.
- Vulnerability databases and npm advisories cover published, indexed issues at scan time, not unknown vulnerabilities, malicious releases, or the entire runtime supply chain. A clean scan is not a penetration test. The protection rules and CSP were verified on one workstation in headless Chromium only.
